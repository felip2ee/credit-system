# actions — Server Actions (`"use server"`) for CRM and platform mutations

Server Actions called from client forms, one file per domain (`holders.ts`, `dossiers.ts`, `consultations.ts`, `users.ts`, `portal.ts`, `scr.ts`, `scr-self.ts`, `settings.ts`, `ai.ts`, `auth.ts`, `bureaus.ts`, `support.ts`, `register.ts`, `account.ts`). Security-sensitive: each is a public POST endpoint.

## Responsibility

Belongs here: exported async functions that validate input, check session and permission, call `src/lib` queries, and call `revalidatePath`. They do not contain SQL (it lives in `src/lib/<domain>/queries`), UI, or schemas (`src/lib/validators`). Co-located tests use `*.test.ts` (`portal.test.ts`, `scr-self.test.ts`).

## Key patterns

- Files start with `"use server"`, so every export is a callable endpoint; keep helpers like `requireHolderWrite()` non-exported.
- Authorization first: `getRequiredSession()` then `hasPermission(session, "holders:write")` (or `"users:manage"` in `users.ts`'s `requireTeamManager()`).
- `getRequiredSession()` throws for a user with `must_change_password`. Helpers such as `requireTeamManager()` and `requireBureauManager()` catch it and return `null`.
- Input is validated with zod before work, using schemas from `src/lib/validators/` (e.g. `holderFormSchema`).
- Result contract: return `{ error: string | null; id?: string }` (`ActionResult`) with pt-BR messages, instead of throwing to the client; DB failures are caught and mapped to a safe message.
- DB work runs through query helpers with a `DbIdentity` or `withUserTransaction` so RLS applies; renamed imports avoid clashing with the action name.
- After writes, call `revalidatePath` for the list and detail routes (`/holders`, `/holders/${id}`); sensitive changes call `writeAuditEvent` in the same transaction and revoke sessions (`users.ts`).
- Password actions write through `setTemporaryCredentials` (`src/lib/auth/credentials.ts`). A missing password only sets the flag. Blank means no password.
- `createBureau` and `inviteBureauAdmin` (`bureaus.ts`), and `inviteTeamMember` (`users.ts`), take an optional `password`. With a password, the user enters at once and no invite e-mail is sent.
- `setBureauAdminCredentials` (`bureaus.ts`) sets an admin password. `setTeamMemberCredentials` (`users.ts`) sets an operator password. The gateway refuses any other target. `setTeamMemberCredentials` also blocks the caller's own account.
- `register.ts` actions are public (no session): `registerClientAction` and `confirmEmailAction`; `account.ts` actions require role `client` and `portal:write` (`requireClient()`).
- `setUserRole` (`users.ts`) only promotes an `operator` to `bureau_admin`. The `protect_profile_identity` trigger refuses other role changes.

## Local conventions

- Tests mock boundaries with `vi.mock` and `vi.hoisted` state: `@/lib/auth/session`, `@/lib/db/permissions`, `@/lib/db/transaction`, `next/cache`, mailer.
- Return a result object for expected failures; `users.ts` `requireTeamManager()` returns `null` when the role lacks `users:manage`.
- External calls (e.g. `lookupCnpj` to BrasilAPI) normalize input with `onlyDigits` first and map HTTP status to a user message.
- Credential actions write audit events (`user.password_set`, `user.force_password_change`, `user.create_with_password`). They never store the password.
