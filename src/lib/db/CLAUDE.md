# db — database access layer: pool, RLS transaction context, role permissions

Single entry point to Postgres for the whole app. Security-sensitive: it sets the identity that Row-Level Security policies read.

## Responsibility

Holds the shared `pg` Pool (`pool.ts`), `withUserTransaction`, `DbIdentity` and `platformIdentity` (`transaction.ts`), and the permission catalog with `hasPermission` (`permissions.ts`). It does NOT hold domain SQL: each domain keeps parameterized queries in `src/lib/<domain>/queries.ts`. Schema, policies and roles live in `db/migrations/`.

## Key patterns

- `withUserTransaction(identity, work)` runs `begin`, then `set_config` for `app.user_id`, `app.user_role`, `app.bureau_id` and `app.support_session_id` (transaction-local), then `work(client)`, then `commit`. The RLS helpers `app_user_id()`, `app_user_role()`, `app_bureau_id()` and `app_support_session_id()` read these values.
- `platformIdentity(identity)` drops `bureauId` and `supportSessionId`. Use it for platform events, which have no Bureau.
- On a failed `rollback`, the error is passed to `client.release(releaseError)` so the broken client is destroyed, not reused (covered in `transaction.test.ts`).
- `DbIdentity.role` is the union `"superadmin" | "bureau_admin" | "operator" | "client"`; `rolePermissions` is `as const satisfies Record<DbIdentity["role"], readonly Permission[]>`.
- `hasPermission(subject, permission)` takes an object with `role` and `supportSessionId`. A superadmin gets operator permissions only in support mode.
- Permissions are `"<resource>:<verb>"` strings from the `permissions` tuple (e.g. `holders:read`, `users:manage`); `Permission` is derived from it.
- `pool.ts` reads `config.databaseUrl` (runtime role), `PG_POOL_MAX` (default 10), and logs a fixed message on pool error (no connection details).
- Auth lookups run `auth_profile_for_session` through `pool`, before any identity exists. It returns `mustChangePassword` with the other profile fields.
- `admin_set_credentials` (migration 009) runs inside `withUserTransaction` through `setTemporaryCredentials`. Its SQL checks the caller and the target, so the TypeScript checks are not the only guard.
- Tests: `*.test.ts` mock `./pool`; `rls.integration.test.ts` and `domain.integration.test.ts` need a real Postgres (`TEST_DATABASE_URL`, `app_runtime` role).

## Applied rules

Rules active in this directory — read them before touching code here:

- @.claude/rules/01-ddd.md — Infrastructure stays out of business rules. Here: no business rules in this layer; it only provides persistence and identity context.

## Local conventions

- Every new permission is added to the `permissions` tuple and to the `rolePermissions` entry of each role that needs it, in the same change; update `permissions.test.ts`.
- Use `set_config(..., true)` (local) only. Never set `app.user_id` on a session level.
- Keep a single Pool instance; import `pool` directly only for queries that run before an identity exists (e.g. auth lookups in `src/lib/auth`).
- A new table needs its RLS policy in `db/migrations/` and a case in `rls.integration.test.ts`.
- Set `profiles.must_change_password` only through `admin_set_credentials` or the password flows. The `protect_profile_identity` trigger (migration 004) enforces this.
