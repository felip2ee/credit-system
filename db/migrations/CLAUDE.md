# migrations — forward-only numbered SQL schema, roles and RLS policies

Source of truth for the Postgres 18 schema. Security-sensitive: roles, grants and Row-Level Security are defined here.

## Responsibility

Holds `NNN_snake_case.sql` files (001–005, 008–035, 038–069 today): roles, Better Auth tables, business tables, RLS, indexes, public SCR authorization, and the grant boundary for cross-tenant functions. It does NOT hold application queries (`src/lib/<domain>/queries.ts`) or the runner (`scripts/db/migrate.mjs`).

## Key patterns

- File name must match `^\d{3}_[a-z0-9_]+\.sql$` (enforced by `loadMigrations`); next number is 070.
- Policy: until the first production deploy the directory is an editable base. From the first production deploy (date: fill in at deploy) it is forward-only with checksum.
- Applied files are immutable: `schema_migrations` stores a sha256 checksum and the runner throws on a mismatch or a missing file. Fix by adding a new migration. A forward-only migration adds a new file and never edits an old one.

- `032_rainha_cred_email_templates.sql` replaces the seeded e-mail templates (`scr_authorization`, `email_verification`, `research_released`, `platform_test`) with Rainha Cred versions: retires the active version only when it is still version 1 (a customized template is never touched; a re-run does nothing). - `025_client_order_ops.sql` holds the client order operations: `cancel_client_order`, `client_order_members` and `record_order_declaration` (definer functions owned by `auth_profile_lookup`, ownership checked in SQL), the table `order_declarations` (append-only, RLS), the `cancelled_by_client` reason, and the `buyer_declaration` legal kind (terms v2 and declaration v1 are provisional text; declaration v2 in `039` removes the provisional mark).
- `044_order_contact_buyer_subject.sql` redefines `open_order` (counter order for the buyer's own holder: account e-mail, typed contact dropped, no `contact_is_buyer`; partner with the buyer's holder document may use the buyer e-mail) and adds `update_order_contact` (staff only; pending authorization of an order in `awaiting_payment`/`awaiting_authorization`; new `public_token`, `auth_code` null, queued notification superseded; in `awaiting_payment` it only saves the contact and a resend without change is `invalid_state`; recipient cap, 2-minute interval and 5 changes per 24 h from `scr_authorizations.contact_changes_at`). The function writes the audit events `order.update_contact` (one per order that shares the authorization) and `order.update_contact_refused` (D12, no contact) itself, under the policy `audit_logs_order_contact_insert`.
- `045_pix_fee_passthrough.sql` passes the Pix fee to the payer: `pix_charges_billing_shape_check` lets a Pix row have `total_charged = amount + fee_amount` (no fee keeps `fee_amount = 0` and `total_charged` null), and `apply_asaas_payment` checks the paid value of a Pix against `coalesce(total_charged, amount)`. The ledger credit, the refund reversal and the affiliate commission still use `amount` (the recharge). `nfse_charge_by_payment` and `nfse_charge_payment` (042/043) already return `coalesce(total_charged, amount)`, so the Pix invoice follows the total with no SQL change.

It recreates `payable_buckets` with `released`, `retained`, `debt`, `in_payout` and `next_release_at`, and `create_payout` takes reversals of any date. Neither redefines `apply_asaas_payment`; the clawback in 041/043/045 uses the same entry set as `create_payout` (`050` extends that set to the coupon kinds).
- `048_coupons.sql` holds the coupons: `coupons`, `coupon_products` and `coupon_redemptions` (forced RLS; the Bureau admin reads and writes, the client reads none), `order_settlements.coupon_id` and `discount`, the payable kinds `coupon_cost` (negative) and `coupon_refund` (positive), and `payable_buckets` and `create_payout` counting them. Permissions `coupons:read` and `coupons:write` are in `src/lib/db/permissions.ts`.
- `049_coupon_money.sql` redefines `reserve_order` (argument `p_coupon_code`), `capture_order` and `release_order`, and adds `coupon_preview` (client preview, no table read) and the internal `coupon_release_redemption`. Lock order: coupon (`coupon:<id>` advisory lock), settlement, client wallet, `payout:<bureau>`, Bureau wallet.
- `050_coupon_clawback.sql` redefines `apply_asaas_payment` so the refund clawback counts `coupon_cost` and `coupon_refund` in the payable balance. Nothing else changes.
- `051_coupon_review_fixes.sql` fixes the coupon review findings: a wallet clawback (refund of a Bureau top-up) no longer blocks coupon orders (`capture_order` follows `reservation_clawed_back`; `coupon_release_redemption` releases `least(funded_wallet, reserved)`); `order_reservation_left` also subtracts the open coupon reservations from the Bureau wallet; `reserve_order` repeats the idempotency check after the coupon lock; the three Bureau wallet entries of a coupon order use reason `cupom`.
- `052_coupon_attempt_limit.sql` limits the coupon code attempts: 10 misses per hour per client. Table `coupon_attempt_misses` (forced RLS, no grant to the app roles; only `auth_profile_lookup` through policies), internal `coupon_attempts_blocked` (also prunes rows older than 1 day). `coupon_preview` is now volatile and records the miss; `reserve_order` only checks the limit and answers `coupon_invalid`.
- `053_coupon_record_miss.sql` adds `coupon_record_miss()` (definer, client session only, no parameters, returns nothing, skips the insert at the limit; `app_runtime` can run it). `placeOrder` calls it from a separate committed transaction (`src/lib/coupons/record-miss.ts`) after a coupon abort that is a code problem, because the rollback undoes the miss that `coupon_preview` wrote.
- `054_coupon_attempt_slots.sql` closes the race in the attempt limit: it counts the ATTEMPT before it checks the code. `coupon_attempt_begin()` (definer, client session only, `app_runtime`) takes `pg_advisory_xact_lock(hashtext('coupon_attempt:' || user))`, prunes, and returns a slot id (a row of `coupon_attempt_misses`, which now has an `id`) or NULL at 10 slots in the last hour. `coupon_attempt_clear(id)` deletes the caller's own slot (success only). A leftover slot counts as a miss (fail closed). `coupon_preview` takes the same lock first, so parallel previews of one client serialize. Internal `coupon_slot_held` (no grant): with the slot id in `app.coupon_slot`, `coupon_preview` and `reserve_order` skip the limit and the preview records no miss. `coupon_record_miss` (053) is dropped. The next migration is 055.

The Bureau no longer writes catalog, cost or affiliate rates.

- `admin_set_credentials(p_target_id, p_bureau_id, p_password_hash)` (009) checks the caller and target in SQL:
  - superadmin: targets only a `bureau_admin` of `p_bureau_id`;
  - bureau_admin: targets only an `operator` of its own Bureau;

  It sets the hash or only the flag, and deletes the target's sessions and pending reset tokens. It returns `false` on a non-match.

## Local conventions

- Never edit an applied migration; add the next number. Never reintroduce Supabase.
- Each file runs in one transaction (the runner wraps it in begin/commit): do not add your own `begin`/`commit`, and avoid statements that cannot run inside a transaction.
- Make role creation idempotent with a `do $$ ... if not exists (select 1 from pg_roles ...)` block.
- Start a file with a comment that states intent when the migration is non-obvious (008, 009).
